1. INTRODUCTION

1.1 Project Overview

AlgoQuest is a comprehensive full-stack web application designed to detect employee burnout before it manifests as attrition. The platform analyzes behavioral metadata from workplace tools (GitHub, Slack, Google Calendar, Gmail) using three specialized engines to provide actionable insights for HR managers and team leads. The application implements a privacy-first architecture where message content is never stored or analyzed—only behavioral patterns (timestamps, activity frequency, network connections) are processed to identify at-risk employees.

1.2 Objectives

  1. To build a deployable full-stack web application for GitHub portfolio and resume
  2. To implement role-based access control with multiple user roles (Employee, Manager, Admin)
  3. To create interactive data visualizations for burnout risk and network analysis
  4. To design a privacy-first architecture compliant with GDPR principles
  5. To demonstrate AI/LLM integration with a 3-agent chat orchestrator

1.3 Theme Adaptation

For this academic submission, the project is presented as an Organizational Health Management Portal—a variation of the Department Event Management Portal theme. Instead of tracking events, the system tracks organizational health indicators and employee wellbeing metrics, providing a modern twist on the traditional management portal concept.

2.2 Current Solutions & Their Failings

Surveillance Tools Reads message content (illegal in EU, destroys trust)
Performance Reviews Happens quarterly while burnout happens weekly

2.3 Proposed Solution

AlgoQuest measures velocity of behavioral change — not absolute values. The system compares each employee against their own personal baseline, ensuring that natural variations (like a night owl consistently working late) are not flagged as burnout. Only sudden shifts from an individual's normal pattern trigger alerts.

Key Features:

  • Three specialized analysis engines (Safety Valve, Talent Scout, Culture Thermometer)
  • Privacy-first architecture (metadata-only, never reads message content)
  • Role-adaptive dashboards for different user levels
  • AI-powered chat assistant with intelligent agent routing

5. DATABASE DESIGN

5.1 Database Architecture

The application uses a Two-Vault Architecture that separates behavioral analytics from identity data at the schema level:

┌─────────────────────────────────────────────────────┐ │ SUPABASE DATABASE │ ├─────────────────────────────────────────────────────┤ │ ┌─────────────────────┐ ┌─────────────────────┐ │ │ │ ANALYTICS SCHEMA │ │ IDENTITY SCHEMA │ │ │ │ (Vault A) │ │ (Vault B) │ │ │ │ │ │ │ │ │ │ • events │ │ • users │ │ │ │ • risk_scores │ │ • tenant_members │ │ │ │ • graph_edges │ │ • teams │ │ │ │ • centrality │ │ • audit_logs │ │ │ │ │ │ │ │ │ │ NO PII │ │ ENCRYPTED PII │ │ │ └─────────────────────┘ └─────────────────────┘ │ └─────────────────────────────────────────────────────┘

5.2 Privacy Implementation

-- Privacy boundary at schema level
CREATE SCHEMA analytics;  -- Vault A: anonymous behavioral data
CREATE SCHEMA identity;  -- Vault B: encrypted PII + RBAC data

Key Privacy Rules:

  • No foreign key constraints between schemas
  • Identity linking via HMAC-SHA256(email + VAULT_SALT)
  • Cross-schema joins require the vault key (not stored in DB)
  • Even database admins cannot connect analytics to identity

5.3 Key Tables

Analytics Schema (Vault A):

Table Primary Key Description
events id Behavioral events (commits, messages, meetings)
risk_scores user_hash Burnout risk metrics
graph_edges id Network connections
centrality_scores user_hash Network centrality metrics

Identity Schema (Vault B):

Table Primary Key Description
users user_hash User identities (encrypted)
tenant_members id Tenant-role mapping
teams id Team definitions
audit_logs id Action audit trail

6. KEY MODULES

6.1 Safety Valve Engine

File: backend/app/services/safety_valve.py

Purpose: Burnout detection using mathematical signals

Metrics Used:

Metric Calculation Threshold
Velocity Linear regression on daily activity scores > 2.5 = CRITICAL
Belongingness Reply rate + mention rate < 0.3 = CRITICAL
Circadian Entropy Shannon entropy of work hours > 1.5 = CRITICAL

Formula:

CRITICAL = velocity > 2.5 AND belongingness < 0.3 AND entropy > 1.5
ELEVATED = velocity > 1.5
LOW = velocity <= 1.5

Status: ✅ Fully Implemented

6.2 Talent Scout Engine

File: backend/app/services/talent_scout.py

Purpose: Network analysis to find structurally critical employees

Metrics:

Metric Description Hidden Gem Threshold
Betweenness Centrality Bridges disconnected teams > 0.3
Eigenvector Centrality Connected to influential people < 0.2
Unblocking Count Times helped others get unstuck > 5

Status: ✅ Fully Implemented with Visualization

6.3 Culture Thermometer

Purpose: Team-level health monitoring using epidemiological model

Model: Adapted SIR (Susceptible-Infected-Recovered) from epidemiology
